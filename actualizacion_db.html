Architectural Decision Record (ADR)

Proyecto: MerxPOS SaaS (Offline-First / Multi-Tenant)

Módulo: Gestión de Terminales y Unidades de Medida

Fecha: 26 de Mayo, 2026

1. Resumen Ejecutivo

El presente documento detalla la resolución respecto a la propuesta de normalización de base de datos para las entidades de Cajas Registradoras (cash_registers) y Unidades de Medida (measurement_units). Si bien se valida la necesidad de normalizar estos datos, se ha procedido con una implementación ajustada a los estándares arquitectónicos del proyecto (Offline-First y Laravel Eloquent), descartando el script DDL original debido a incompatibilidades críticas con el sistema distribuido.

2. Análisis de la Propuesta Original (Riesgos Identificados)

Incompatibilidad con Arquitectura Distribuida (Offline-First)

La propuesta sugería el uso de llaves primarias auto-incrementables (serial). En MerxPOS, el cliente PWA (Tauri/Dexie) necesita generar registros sin conexión a internet. El uso de secuencias seriales en PostgreSQL impide la sincronización asíncrona, ya que el cliente no puede predecir el siguiente ID disponible, generando colisiones al reconectar.

  • Ruptura del Aislamiento Multi-Tenant: La llave foránea sugerida para identificar la tienda (fk_store_id) apuntaba a la tabla users(id). En nuestro esquema SaaS, el aislamiento de datos exige que la relación se haga mediante tenant_id (UUID) apuntando a la tabla stores(id).
  • Antipatrones de Framework: El uso de enteros (smallint) para deleted y campos de auditoría manuales (fk_user_register_id) en tablas de catálogo transaccional sobrecarga el modelo de dominio y choca con el manejo nativo de Eloquent (SoftDeletes y timestamps).
  • Incoherencia de Dominio: Atar un producto global (items) a un usuario de caja físico (fk_cash_register_user_id) viola el principio de diseño de inventario, donde los productos pertenecen a la tienda (Tenant), no a un turno de caja específico.

3. Solución Implementada

Se crearon dos nuevas migraciones y modelos (Terminal y MeasurementUnit) que satisfacen la necesidad de negocio planteada por el DBA, pero respetando estrictamente el motor de sincronización.

Resolución Técnica Adoptada
  • Llaves Primarias UUID (v4): Garantiza que el frontend offline pueda insertar registros locales (IndexedDB) de forma segura y sincronizarlos posteriormente sin conflictos de ID.
  • TenantScope Global: Ambas tablas incluyen tenant_id como llave foránea hacia stores. El ORM vigila a nivel global que ningún usuario pueda consultar cajas o medidas de otro Tenant.
  • Índices Compuestos (Unique): Se implementó UNIQUE (tenant_id, code). Esto permite que la "Tienda A" y la "Tienda B" tengan ambas una caja con el código CAJA_01 sin colisiones a nivel de base de datos.

4. Estructura de Datos Final Aprobada

Tabla PK Aislamiento Campos Clave Auditoría / Estado
terminals id (UUID) tenant_id (FK stores) name (varchar), code (varchar) is_active (bool), deleted_at
measurement_units id (UUID) tenant_id (FK stores) name (varchar), abbreviation (varchar) deleted_at
